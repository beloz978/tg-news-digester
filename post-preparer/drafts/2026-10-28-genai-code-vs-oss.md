🤖 **GenAI-код vs Open Source: когда контрибьюция превращается в нагрузку**

За последний год количество коммитов на GitHub выросло примерно в 15 раз, а программистов больше не стало (цифра Егора Бугаенко). Генерация кода почти бесплатна. Проверка, интеграция и сопровождение по-прежнему стоят времени людей. И модель OSS «нашёл → исправил → прислал PR» начинает ломаться.

**1️⃣ Ворота закрываются**
Никита Соболев (@opensource_findings) собрал хронику:
• CPython: не больше 3 открытых PR у внешнего контрибьютора;
• OpenJDK запретил AI-assisted PR, Godot и Zig запретили использование AI;
• Node.js будет молча закрывать AI-PR;
• Litestar, Hono, Ladybird закрыли PR извне; Sindre Sorhus закрыл свои проекты;
• Jazzband перестал принимать новых участников («слопокалипсис»);
• GitHub ввёл лимит открытых PR для пользователей без write-доступа;
• curl, Google OSS VRP, Intel и HackerOne свернули bug bounty;
• Hacktoberfest засчитывает только митапы, а не PR.
Вывод Соболева: «опенсорс, каким я его знал, мёртв».

**2️⃣ Три стратегии мейнтейнера**
@pylounge, комментируя закрытие PR в Litestar, видит три варианта:
🔹 модерировать лавину AI-PR руками, и этот вариант всё менее реален;
🔹 отдать всё агентам: рискованно и спорно;
🔹 принимать PR только от узкого круга. Ставка автора на этот вариант, то есть Open Source → «Open Close Source».
Бонус-прогноз: крупные компании, пока токены дёшевы, будут делать свои внутренние форки («GigaLitestar»).

**3️⃣ Противоположный полюс: «принципы, от которых пришлось отказаться»**
Егор Бугаенко идёт по второму пути до конца:
• **Ручное ревью и триаж вредят проекту.** В его репозиторий на ~1,5k звёзд приходит около 100 баг-репортов в день. Агент сам триажит их и мержит 40–50 PR в день «вслепую». Сложные и радикальные изменения эскалирует человеку, таких несколько в день.
• **Вежливость больше не нужна.** «В PR не программист, а курьер»: close без объяснений, обижаться некому.
• **Авто-reject вместо дискуссий.** PR больше 200 строк получает красный CI. Агент сам разобьёт его на части.
• **Не читать код, читать impact.** Тесты переписаны на YAML-фикстуры «вход → выход», чтобы изменение поведения было видно глазами. CI должен показывать, к чему приводит PR (метрики, производительность, артефакты), а не дифф.
• **Скорость важнее стабильности.** Preflight build умер: 100 PR × 10 минут сборки не помещаются в сутки. Мастер ломается примерно 2 раза в день, и его чинит агент.
• Плюс: комментарии в коде запрещены линтером («роботу они мешают»), legacy-кода нет (400 тикетов за 10 лет закрыты Claude Code за неделю).

**4️⃣ На самом деле это одна проблема**
Обе стратегии отвечают на один и тот же дефицит: **внимание мейнтейнера**.
Закрыть ворота значит защитить внимание людей. Подход Бугаенко заменяет внимание формальными контролями: лимиты, фикстуры, impact-отчёты, zero tolerance в CI.
Общий знаменатель: проверку изменения нужно формализовать. Иначе она не масштабируется.

Хорошая агентская разработка поэтому не
`Prompt → Code → PR`,
а
`Spec → Agent → Tests → Evidence → PR`,
где автор (человек или агент) приносит доказательство, а не только дифф.

Для Data Engineering это особенно наглядно. Агент за минуты напишет dbt-модель или Dagster asset. Но «impact» в DE — это не дифф SQL, а дифф данных: row counts, data contracts, сверка с прошлым прогоном, стоимость запроса. YAML-фикстуры Бугаенко по сути те же dbt unit tests: показываешь вход и ожидаемый выход, и ревьюер видит смысл изменения, не читая код.

💡 **Предварительный вывод**
Раньше OSS упирался в число людей, способных написать код. Теперь он упирается в способность проверять, понимать и сопровождать изменения. Ценнее всего становится не тот, кто шлёт больше PR, а тот, кто приносит проверенное изменение с минимальной нагрузкой на мейнтейнера. Либо тот, кто автоматизировал эту проверку у себя в CI.

А вы на чьей стороне: закрывать ворота или строить AI-native конвейер приёма изменений?
