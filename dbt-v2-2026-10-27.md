**dbt v2: что изменилось для инженера данных — 1/4**
*Разбор на 27 октября 2026. В фокусе DuckDB, несколько движков, стоимость разработки и открытость.*

Мой главный вывод: dbt усиливает цикл «написал SQL → проверил локально → запустил». Но готовность этой схемы зависит от адаптера, режима анализа и конкретной функции.

**Что уже описано в документации**
• Rust-движок и ADBC-драйверы меняют устройство CLI и адаптеров. Ускоряются parse/compile; само по себе это не обещает ускорить SQL в вашем warehouse.
• Ошибочные YAML-ключи и конфигурации теперь проверяются строже. Ранее незаметная опечатка может остановить миграцию.
• `dbt lint` использует конфигурацию и коды правил SQLFluff.
• Совместимые data tests можно объединять через `--batch-tests`. Экономию на своём проекте всё равно нужно измерять.

**Метаданные становятся обычными данными**
Information Schema сохраняется в Parquet; её можно читать локальным DuckDB. После parse доступны определения проекта, после compile — больше сведений; типы и lineage колонок требуют strict analysis. Runtime-результаты появляются после run/build.

Это даёт понятные сценарии: найти модели без описаний, проверить стандарты проекта, дать агенту структурированный контекст. Встроенные checks проверяют правила проекта; data tests по-прежнему проверяют данные.

**Важное различие дистрибутивов**
Стандартный `dbt` и Apache-2.0-дистрибутив `dbt-oss` — разные поставки. По install guide в OSS отсутствуют SQL comprehension/static analysis, LSP и встроенный lint. У стандартного dbt режим strict требует `dbt login`; без входа он откатывается к baseline. Поэтому «бесплатно» и «все функции в Apache-версии» — разные утверждения.

**DuckDB и multi-engine в dbt v2 — 2/4**

За словом «локально» скрываются разные возможности.

**1. Запуск моделей на DuckDB**
В v2 встроен DuckDB-адаптер для CLI. Можно строить модели в локальной базе. Это продолжение существовавшего сценария dbt-duckdb, а не первое появление DuckDB в экосистеме. Наличие локального движка само по себе не переносит BigQuery- или ClickHouse-специфичный SQL.

**2. Unit-тесты warehouse SQL на DuckDB**
Добавлен экспериментальный `compute: local` с флагом `DBT_ENGINE_EXPERIMENTAL_LOCAL_UNIT_TESTS=true`.

Сейчас документация ограничивает этот путь BigQuery и Snowflake. Тест использует fixtures, но при первом запуске dbt получает схемы upstream-таблиц из платформы и затем кеширует их. Нужен strict analysis; неподдержанная функция может сорвать перевод в DuckDB. Автоматического fallback в warehouse нет.

Практический смысл: быстро проверять бизнес-логику SQL. Проверку настоящего MERGE, прав, типов и поведения production-движка следует оставлять интеграционному прогону. Полностью автономный offline-дебаг любого DWH из этого не следует.

**3. Разные адаптеры в одном запуске**
Такой режим теперь заявлен, но тоже экспериментален: `DBT_ENGINE_EXPERIMENTAL_MULTI_ADAPTER=true`. Его нельзя приравнивать к давно существующему переключению dev/prod targets.

Для обмена таблицами между платформами cross-platform Mesh описывает общий Iceberg-каталог и синхронизацию метаданных. Маршрутизация вычислений и доступ движков к одним данным — две отдельные задачи. Произвольный JOIN BigQuery + ClickHouse + Spark не возникает от одного флага.

**Что показал свежий практический кейс**
В связанном с Reddit разборе Greybeam авторы собрали Snowflake ↔ DuckDB на общих Iceberg-таблицах. Но multi-adapter на версии 2.0.6 у них упал с `drop_indexes_on_relation`; рабочий пример использует отдельные invocations. Это результат их конфигурации и версии, а не доказательство неисправности всех релизов.

**dbt v2 vs SQLMesh vs OpenDBT vs Bruin — 3/4**
*Ниже — инженерная оценка по задачам, а не рейтинг «кто быстрее».*

**dbt v2 — развитие существующего dbt-проекта**
Сохраняет язык моделей и DAG, усиливает анализ SQL и локальную обратную связь. Local unit tests и multi-adapter стоит оценивать как эксперименты. Для открытости сравнивайте именно состав dbt и dbt-oss, а не только название движка.

**SQLMesh — управление изменениями и пересчётами**
Plan показывает затронутые модели и необходимые backfill-интервалы до применения. Virtual environments позволяют переиспользовать неизменённые физические таблицы. Есть SQL/Python-модели и unit-тесты; Есть тестирование на DuckDB, а test connection можно заменить.

Multi-engine документирован через gateways и выбор gateway у модели. При общем virtual layer нужен доступ к общему каталогу; при раздельных каталогах можно использовать gateway-managed virtual layer. Это не автоматическая доставка данных между любыми базами.

Мой выбор для PoC: SQLMesh, если главный риск — корректно и экономно пересчитать историю после изменения логики. Проверять нужно и накладные расходы state/virtual layer, и поддержку нужного движка.

**OpenDBT — расширение Python dbt Core**
Здесь имеется в виду `memiiso/opendbt`. Проект динамически расширяет Python-код dbt Core, добавляет local Python/dlt, каталог и интеграции. В зависимостях есть dbt-duckdb.

Это интересный путь для существующего Python-стека. Из его README не следует совместимость патчей с Rust-runtime v2. Я бы фиксировал версии и отдельно проверял совместимость; обещать ему все новые возможности v2 оснований нет.

**Bruin — один проект для ingestion + SQL/Python + quality**
Есть ingestr, изолированные Python-окружения, DuckDB, lineage и проверки. У asset задаются тип и connection: можно организовать шаги на разных платформах, включая BigQuery и ClickHouse.

Мой выбор для быстрого end-to-end MVP: проверить Bruin первым, если хочется уменьшить число отдельных инструментов. Но multi-platform DAG сам по себе не означает единую семантику SQL или автоматический обмен таблицами. Трансферы и границы движков нужно проектировать явно.

**Что это меняет для гибридной платформы — 4/4**
*Выводы для стека BigQuery + ClickHouse + Trino/Spark и разработки с DuckDB.*

**Четыре тенденции, которые имеет смысл проверять на практике**

• **DuckDB как быстрый цикл разработки.** Проверять бизнес-логику на маленьких fixtures локально; отдельно проверять материализации, специфичные функции и стоимость на целевом движке. Локальные тесты полезны, когда чётко понятны их границы.

• **Общие таблицы вместо копий на каждый движок.** Iceberg/каталог могут дать нескольким engines доступ к одним данным. Но остаются совместимость формата, права, refresh метаданных и особенности записи. Выбор engine у модели не решает всё это автоматически.

• **Метаданные для coding agents.** Parquet Information Schema даёт агенту SQL-интерфейс к проекту. В dbt v2 через packages можно доставлять SKILL.md: `dbt deps` устанавливает инструкции для выбранного `ai_provider`, в том числе Codex и Claude. Мой вывод: ценность в коротком проверяемом цикле изменения, а не только в генерации SQL.

• **Экономия на пересчётах.** SQLMesh имеет явный plan/backfill-процесс. У dbt следует отдельно оценивать incrementals и dbt State, у Bruin — интервалы и стратегии материализации. Наличие одного флага или CLI ещё не означает одинаковую модель управления состоянием.

**Что делать с BigQuery + ClickHouse сейчас**
В текущем upgrade guide ClickHouse для v2 помечен private beta, Spark — beta и CLI only. Поэтому для ClickHouse-платформы я бы начал с отдельного PoC, сохранив рабочий v1-путь. Для BigQuery уже интересно проверить local unit tests, учитывая login/strict и необходимость upstream-схем.

План проверки: 5–10 показательных моделей, одни fixtures и edge cases, сравнение результата на DuckDB и production-engine, затем incremental rerun/backfill. Замерить parse/compile, стоимость CI и корректность повторного запуска. Эти результаты полезнее общего обещания «Rust всё ускорит».

В свежем треде о зрелости dbt 2 обсуждают скорость парсинга, документацию и совместимость пакетов. Это опыт участников, а не независимый benchmark. Статусы адаптеров и функций выше сверены с официальной документацией; собственный production-прогон этих стеков здесь не выполнялся.
